# 16.3 Test-Time Scaling

16.2 节训练出了更常展开推理的模型。部署时却会遇到一个新问题：同一个模型面对“把 hello 翻译成中文”和一道 AIME 题，如果都生成一万 token，前者浪费计算，后者又未必足够。

参数已经固定以后，系统仍有三种增加计算的方法：并行生成更多候选，让一条答案反复修订，或在多个中间步骤之间搜索。它们都属于 **Test-Time Compute Scaling**。本节继续沿着一道数学题，先解释额外计算为什么可能有效，再分别观察三种用法，最后讨论收益何时饱和以及怎样设置停止条件。

## 1. 推理时为什么要增加计算

模型一次生成失败，可能有两种原因：它没有掌握所需知识，或者它掌握了方法，却在这次采样中选错路线、算错数字。增加推理计算只能缓解第二类问题。先区分训练计算和单次任务计算，才能知道额外预算应该放在哪里。

训练计算与推理计算发生在不同阶段。训练计算更新参数，使模型掌握新的知识和策略；推理计算保持参数不变，只在当前题目上增加采样、检查或搜索。二者不能按 FLOPs 直接互换。

早期语言模型通常一次生成一条较短答案。推理模型允许在同一题上生成更长的轨迹或更多候选，于是推理计算从固定成本变成可以分配的预算。问题随之变为：在模型能力已经确定以后，哪一种分配方式最能提高当前任务的成功率？

### 1.1 Snell 等人的预算实验

[Snell et al. 2024](https://arxiv.org/abs/2408.03314)（“Scaling LLM Test-Time Compute Optimally”）系统比较了不同推理预算和分配策略：

**实验设置**：固定一个 base model（Llama-3-8B-Instruct），在不同难度的数学题上，比较两种提升方式：

- **方式 A**：用更多推理算力——让模型生成 N 个候选解，用 verifier 选最好的（best-of-N）
- **方式 B**：改用更强的模型，比较推理计算与模型能力带来的收益

实验得到三个主要结果：

1. 在论文给定的模型和数学数据上，恰当分配推理计算可以让较小模型超过计算量更高但分配不佳的基线；
2. 基座模型很少产生正确候选的题目，继续增加有限预算的收益会下降；
3. 合适的策略随题目难度和验证器质量变化，不能对所有题目固定使用一种方案。

训练完成以后，模型参数已经固定，推理阶段仍可调节候选数和修订次数。因此，同一个模型可以给简单任务较小预算，给较难任务较大预算。实验同时说明这种调节受基座能力限制：模型一次也生成不出正确方法时，重复采样的帮助很小。

## 2. 推理计算可以花在哪里

固定一份预算以后，最直接的选择是“多走几条路”或“沿一条路继续修改”。树搜索则把两者结合：先产生多个中间分支，再把预算集中到评分较高的路径。

### 2.1 并行采样

让模型独立生成 N 个候选解，然后用一个 verifier 选最好的。这是 best-of-N 的思路。

假设模型每次独立生成正确答案的概率是 $p$，采样 $N$ 次至少出现一个正确答案的概率为

$$
P(\text{至少一次正确})=1-(1-p)^N.
$$

因为 $N$ 次全部错误的概率是 $(1-p)^N$，用 1 减去它即可。例如 $p=0.2$、$N=5$ 时，至少出现一个正确答案的概率约为 $1-0.8^5=67.2\%$。这只是候选覆盖率；最终还需要 verifier 把正确候选选出来。

```python
# 并行采样示意
candidates = [model.generate(prompt) for _ in range(N)]
scores = [verifier.score(prompt, c) for c in candidates]
best = candidates[argmax(scores)]
```

候选彼此独立时可以并行生成，增加 $N$ 会提高覆盖正确答案的机会。代价是生成与评分计算随 $N$ 增长，而且系统必须有可靠 verifier 才能把正确候选选出来。这正是 [第 17 章 PRM](../chapter20_prm_search/outcome-vs-process) 要处理的问题。

### 2.2 顺序修订

并行采样每次都从题目重新开始，无法利用上一版已经完成的工作。顺序修订先生成一个初始解，再要求模型找出其中的问题并产生下一版：

```python
# 顺序修订示意
solution = model.generate(prompt)
for _ in range(K):
    feedback = model.critique(prompt, solution)
    solution = model.revise(prompt, solution, feedback)
```

顺序修订复用上一版答案，适合错误能够被指出、局部修改又比从头生成便宜的任务。每轮依赖上一轮，因此延迟按轮数累积；如果批评本身错误，后续版本还可能离正确答案更远。实际系统仍可加入外部 verifier 检查是否值得接受修改。

### 2.3 树搜索

并行采样会重复相同前缀，顺序修订又可能一直困在同一条错误路线。树搜索把推理过程展开成节点：每个节点保存一个中间步骤，系统可以从同一前缀尝试多个后续，并用 verifier 决定保留哪些路径。具体算法放在 [17.5 推理时搜索](../chapter20_prm_search/inference-time-search)，这里先记住它解决的是“怎样复用中间结果”。

## 3. Deep Think 如何把并行推理做成产品

前两节把并行候选当作多次独立调用。实际系统还要解决另一个问题：多条路径怎样共享 GPU、何时停止，以及最后由谁整合结论。Deep Think 可以作为并行推理产品化的案例来观察。

Google 对 [Gemini Deep Think](https://blog.google/products-and-platforms/products/gemini/gemini-2-5-deep-think/) 的公开说明提供了一个产品案例：系统用并行思考技术同时考虑多个假设，并允许这些候选在最终回答以前被修订或组合。公开资料没有披露完整算法，因此不能直接断定内部使用了 Best-of-N、树搜索或某种跨路径注意力。

可以从接口行为抽象出三项系统工作：

- 同时生成多条独立的推理路径
- 比较或组合不同路径中的信息；
- 在预算内决定何时停止并生成最终回答。

若 $N$ 条路径分配到独立计算资源上，它们可以并行生成；总计算量仍随路径数增加，端到端速度还取决于调度、聚合和硬件利用率，不能直接按 $N$ 倍换算。

### 3.1 产品分数为什么不能直接解释算法

Google 报告专用 Deep Think 版本在 2025 年 IMO 达到金牌区间，后续版本也公布了 HLE、ARC-AGI-2 和 Codeforces 等成绩。这些结果说明并行思考可以成为有效的推理预算方案，却不能单独证明收益来自多少条路径或哪一种聚合算法。评测还可能使用代码执行、搜索和不同预算，比较模型时必须同时记录这些条件。

对课程而言，更重要的结论是：并行路径缩短的是墙钟等待时间，不会消除总计算量。路径越多，系统越需要处理 GPU 调度、候选去重、评价器吞吐和停止条件。

### 3.2 并行路径怎样停止

固定生成 $N$ 条路径最容易实现，却会让已经形成一致答案的简单题继续消耗预算。动态系统可以在每一批候选结束后检查三项信息：是否已经出现可验证答案，高分候选之间是否一致，继续增加一批候选能否带来新的方法。答案已经通过外部检查且候选趋于一致时可以停止；候选仍然冲突、验证器又无法区分时，继续采样的价值通常很低，此时更需要工具、搜索或人工规则补充反馈。

这个停止逻辑不会由“并行思考”四个字自动获得。它必须与任务验证器、最大 token、墙钟超时和失败回退一起设计。

## 4. 何时停止增加推理计算

候选数、修订次数和搜索节点都能继续增加，但正确率不会一直按相同比例上升。部署需要比较“下一份计算还能提高多少成功率”和“它会增加多少延迟与费用”。

额外计算会增加生成 token、验证调用和硬件占用，但延迟不一定与总计算量同比增长：并行采样可能用更多 GPU 换更短等待，顺序修订则会直接增加串行轮数。部署时应同时记录任务成功率、墙钟延迟、总 token、验证器调用数和费用。

任务名称也不能直接决定预算。同一道代码题，已经有完整测试时可以并行生成候选；缺少测试时，继续采样可能只会产生更多无法区分的答案。设置预算前应先判断验证器是否可靠、单次成功率是否足够，以及任务失败的代价。

这也构成了 [16.4 Hybrid Thinking 与预算控制](./hybrid-thinking) 的工程动机：根据任务难度选择推理模式和预算。

### 4.1 收益为什么会逐渐下降

额外计算的收益取决于“继续尝试是否还能找到新的正确路径”。简单题在少量计算后已经答对，继续生成只会重复；中等题可能通过更多候选或一次修订纠正偶然错误；超出基座能力的难题则会反复产生相似的错误。Snell 等人的预算实验表明，最合适的分配方式随题目难度和验证器变化，固定增加候选数不会保持同样的边际收益。

因此，test-time compute scaling 不能无限替代 training compute scaling。两者互补：

- training compute 决定**能力上限**
- test-time compute 决定**接近上限的程度**

如果基座模型没有掌握解题所需的知识或操作，增加采样和修订次数也难以产生正确路径。因此，推理计算依赖基座模型已经具备的能力。

## 小结

Test-time Compute Scaling 提供了三种可以直接调节的资源：并行候选数量、单条推理链的修订次数和搜索树的规模。任务越难，增加这些资源越可能带来收益；基座能力不足或任务已经很简单时，收益会很快降低。

下一节把这条规律用于部署：同一个模型怎样在直接回答与深度思考之间切换，并用思考预算限制延迟和成本。
