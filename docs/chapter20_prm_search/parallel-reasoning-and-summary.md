# 17.6 并行推理与答案汇总

17.5 节沿着一棵搜索树共享前缀并逐步选择路径。它适合中间状态容易保存和评分的任务，却需要频繁等待“生成一步—评分—再生成”。如果计算资源充足，也可以让多条完整推理同时运行，最后再比较它们。

例如，同一道数学题可以同时尝试因式分解、求根公式和配方法。多数投票只统计三个最终答案，协调模型还可以检查每条路径的依据，并在一条路径算术正确、另一条路径解释更清楚时整合结果。

本节先比较串行深度与并行广度，再用 PaCoRe 说明协调器怎样读取多条路径，随后把这种协调器推广到 GenRM 与 LLM-as-Judge，最后把第 17 章的 verifier 和推理策略放回一套选择顺序。

## 1. 推理算力如何分配给深度与广度

固定总 token 预算以后，可以让一条路径思考更久，也可以生成多条较短路径。前者保留连续状态，后者增加方法多样性。任务是否有多个可行解、各路径能否并行执行，以及最后有没有可靠聚合器，会共同决定选择。

[第 16 章 Test-time Compute Scaling](../chapter19_reasoning/test-time-scaling) 我们讨论过两种推理算力的花法：

- **串行深度（Sequential Depth）**：模型生成一条很长的 CoT
- **并行广度（Parallel Breadth）**：模型生成多条独立的 CoT，用某种方式聚合

| 方式     | 代表                        | 算力分配             | 适合的任务                             | 主要代价                                 |
| -------- | --------------------------- | -------------------- | -------------------------------------- | ---------------------------------------- |
| 串行深度 | 长推理、顺序修订            | 一条路径连续保留状态 | 后一步依赖前一步的证明、代码与工具任务 | 轮数增加会累积墙钟延迟，早期错误也会传播 |
| 并行广度 | Best-of-N、Self-Consistency | 多条路径独立生成     | 存在多种独立解法且结果容易比较的任务   | 总计算随路径数增加，还需要可靠聚合器     |

并行广度可以用更多硬件缩短等待时间，但不会减少总计算量。资源不足时，多条路径也会排队执行。

**PaCoRe** 同时生成多条推理，把它们压缩成消息，再让下一轮并行路径读取这些消息。它与多数投票的差别在于：前一轮的多条思路会进入下一轮推理，而最终系统也不只统计答案出现次数。

### 1.1 PaCoRe 怎样协调多条推理

[PaCoRe](https://github.com/stepfun-ai/PaCoRe)（StepFun，2026 技术报告）用多轮消息传递扩展并行推理。设每轮并行路径数为 $K_r$，例如配置 `[32, 4]` 表示第一轮生成 32 条路径，压缩以后第二轮再生成 4 条协调路径。

#### 每一轮怎样交换信息

```text
┌─────────────────────────────────────────────────────┐
│ Step 1: 第 r 轮并行生成 K_r 条推理                   │
│   - 输入原问题与上一轮压缩消息                       │
│   - 各路径独立探索                                  │
├─────────────────────────────────────────────────────┤
│ Step 2: 把本轮路径压缩成协调消息                     │
│   - 保留候选方法、冲突与中间结论                     │
│   - 控制消息长度，使下一轮仍能放入上下文             │
├─────────────────────────────────────────────────────┤
│ Step 3: 未到最后一轮则继续；最后一轮生成答案         │
│   - 训练时用 outcome reward 评价最终结果             │
└─────────────────────────────────────────────────────┘
```

#### 协调器与投票的差别

PaCoRe 与 Best-of-N + Majority Vote 的差别在于信息怎样继续流动：

- **Majority Vote**：选择出现次数最多的答案（简单统计）
- **PaCoRe**：压缩多条推理中的方法与冲突，让后续一轮继续修正和综合

协调器可能带来两点帮助：

- **处理等价答案**：多条路径写法不同但结论等价时，协调器可以比较语义；多数投票需要先把答案规范化
- **比较推理依据**：两条路径得到相同答案时，协调器仍可检查中间步骤；判断质量仍受协调模型能力限制

#### 训练 PaCoRe

PaCoRe 使用结果奖励训练协调与综合能力，不要求逐步 PRM 标签。奖励只说明最终答案是否正确，训练算法还要估计哪些路径和消息促成了结果。

```python
def pacore_reward(prompt, target_answer, round_widths):
    message = ""
    for round_id, width in enumerate(round_widths):
        reasonings = [model.generate(prompt, message) for _ in range(width)]
        if round_id < len(round_widths) - 1:
            message = coordinator.compact(prompt, reasonings)
        else:
            final_answer = coordinator.answer(prompt, reasonings)

    reward = 1.0 if final_answer == target_answer else 0.0
    return reward
```

这段伪代码只展示数据流。实际实现会区分中间协调消息和最终答案，并记录相应生成概率；一个结果奖励不会自动、等量地传给所有路径。

## 2. 三种推理结构如何选择

协调器能够利用多条完整路径，但它不复用共同前缀；树搜索能够复用节点，却增加串行评分。下面把 PaCoRe、并行思考和 MCTS 放在同一张表中，比较计算结构而不是只比较最终分数。

PaCoRe 报告用同一个 8B 模型形成三档推理配置：`[4]`、`[16]` 和 `[32,4]`。高档配置在 AIME 2025 上达到 93.7%，总 test-time compute 约 187 万 token；在 HMMT 2025 上达到 94.5%，约 180 万 token。作为训练起点的 RLVR-8B 分别为 84.1% 和 75.4%，但只使用约 5 万 token。

这组结果说明训练后的协调模型能够继续从更宽的并行计算中获益，也说明提升并不便宜：高档配置使用的 token 数比单链基线高一个数量级以上。比较方案时必须把正确率、总 token、墙钟延迟和并行硬件一起报告。

### 2.1 三种推理结构的系统差别

三种推理结构的对比：

| 维度     | PaCoRe                 | 公开的 Deep Think 接口               | MCTS                          |
| -------- | ---------------------- | ------------------------------------ | ----------------------------- |
| 推理结构 | 多轮并行路径与压缩消息 | 并行考虑多个假设，内部算法未完整公开 | 显式树形状态与重复访问        |
| 预算控制 | 每轮路径数和轮数       | 产品 effort 或模式                   | 迭代数、扩展数与 rollout 长度 |
| 反馈     | 训练主要使用结果奖励   | 公开资料未披露完整结构               | 结果、PRM 或外部 verifier     |
| 主要代价 | 大量完整轨迹与消息压缩 | 难以复现内部协调                     | 串行选择、状态维护与多次评分  |

### 2.2 PaCoRe 适合哪些任务

PaCoRe 适合能够并行尝试多种方法、又能用最终答案可靠判分的任务。它不要求逐步 PRM，却需要训练模型学会压缩和综合；并行路径数增加时，总计算近似随之增长，性能也不会保证线性提高。若一条路径必须频繁读取工具状态，或者中间错误需要立刻停止，17.5 的树搜索与逐步验证通常更合适。

## 3. 生成式模型如何评价并汇总答案

协调器需要完成两项工作：判断每条回答有什么问题，并把多条证据压缩成一个结论。若它只输出标量，系统很难检查聚合依据；让模型生成评价文本，再从判断 token 得到分数，就得到更一般的 **GenRM（Generative Reward Model）**。

传统奖励模型直接输出标量。GenRM 先生成评价文本或判断 token，再从生成概率中得到分数，因此可以同时保留数值判断和解释。

### 3.1 GenRM 的输出形式

```text
输入：prompt + response + "请评价这个回答"
输出：自然语言评价 + [GOOD/BAD]
```

GenRM 可以读取判断位置上 GOOD token 的概率，把生成判断转换成数值奖励：

$$\text{GenRM}(q, o) = P(\text{"good"} | q, o, \text{prompt})$$

这里 $q$ 是问题，$o$ 是待评价回答，最后一个 `prompt` 表示评价指令。模型在 GOOD/BAD 位置给 GOOD 的概率越高，奖励越高。若比较两个回答，也可以让模型输出 A 或 B，并对两个 token 的概率归一化。自然语言解释用于检查判断依据，进入训练的则是可比较的数值或标签。

### 3.2 GenRM 与判别式 RM

| 维度 | 判别式 RM                  | GenRM                                |
| ---- | -------------------------- | ------------------------------------ |
| 输出 | 标量、类别或偏好概率       | 评价文字与判断 token                 |
| 训练 | 回归、分类或排序损失       | 下一个 token 预测，可配合偏好数据    |
| 调试 | 主要依赖分数分布和错误样本 | 可以阅读评价依据，但仍要验证其正确性 |
| 推理 | 一次前向即可得到分数       | 需要生成若干评价 token，通常更慢     |

### 3.3 GenRM 与 PRM 的关系

GenRM 是一个更宽泛的概念——它可以做 ORM（输出整条回答的评价）或 PRM（输出每步推理的评价）。

[17.3 节的 ThinkPRM](./generative-prm) 是 GenRM 做 PRM 的代表。其他 GenRM 工作：

- **Generative Verifiers**（[Zhang et al.](https://arxiv.org/abs/2408.15240)）：用 Chain-of-Thought 评价
- **LLM-as-Judge**（[Zheng et al.](https://arxiv.org/abs/2306.05685)）：用 GPT-4 评价其他模型的输出

### 3.4 LLM-as-Judge 与 Self-Rewarding

LLM-as-Judge 是 GenRM 的一种常见用法：用较强 LLM 评价候选输出。

#### LLM-as-Judge 的应用

- **benchmark 评测**：用 GPT-4 作为 MT-Bench、AlpacaEval 的裁判
- **训练数据筛选**：用 LLM 过滤高质量训练数据
- **RLHF 替代**：用 LLM 替代人类标注偏好数据（RLAIF）

#### Self-Rewarding Language Models

[Self-Rewarding LM](https://arxiv.org/abs/2401.10020)（Meta 2024）让模型参与评价自己的候选回答：

```python
def self_reward_training(prompt, model):
    # 1. 生成多个回答
    responses = [model.generate(prompt) for _ in range(N)]

    # 2. 让模型自己评价
    rewards = [model.judge(prompt, r) for r in responses]

    # 3. 用自评价做 RL（DPO 或 PPO）
    model = rl_update(model, prompt, responses, rewards)
```

这种方法不必单独训练一个固定奖励模型，但仍需要评价提示、初始监督和独立评测。生成与评价来自相近模型时，自我评价可能强化已有偏差：模型不容易识别自己尚未掌握的错误。

## 4. 如何组合 Verifier 与推理策略

走到这里，方法选择可以回到一条具体决策线：先确定什么结果能够可靠验证，再判断是否需要定位中间错误，最后决定额外计算用于树的深度还是并行路径的广度。

四种变化分别发生在不同层次：

### 4.1 从判别到生成

判别式 PRM 输出固定标签，生成式 PRM 给出判断依据，自我评价复用当前模型。越依赖模型自身判断，越要用外部测试检查系统性偏差。

### 4.2 从深度到广度

Tree of Thoughts 和 MCTS 复用中间节点，PaCoRe 在广度上并行生成完整路径。前者适合逐步反馈可靠的任务，后者适合多条完整解法可以相互比较的任务。

### 4.3 从静态到动态

固定 PRM 可以为每一步评分；自适应搜索还会根据分数差异决定把后续预算分给哪些路径。

### 4.4 从单一到混合

结果奖励、过程奖励、形式检查和 LLM 评价覆盖的错误不同。混合使用时要明确每个分数在哪一层生效，并处理量纲和冲突。

## 本章总结

第 17 章从“第六步漏掉平方、最终答案却可能碰巧正确”开始，逐步补上训练与推理需要的反馈：

- **17.1 结果奖励与过程奖励**：稀疏奖励问题与信用分配
- **17.2 判别式 PRM**：Let's Verify 与 PRM800K
- **17.3 生成式 PRM**：ThinkPRM 的自然语言评价与标签效率
- **17.4 形式化 Verifier**：AlphaProof、Lean4 与 DeepSeek-Prover-V2
- **17.5 推理时搜索**：Beam Search、ToT、MCTS 与 AlphaCodium
- **17.6 并行推理与答案汇总**：PaCoRe、GenRM 与 LLM-as-Judge

面对一个新任务，可以依次问五个问题：

1. 最终答案能否自动验证？能验证时，先建立可靠 ORM；
2. 错误是否会在长轨迹中传播？会传播时，再考虑步骤反馈；
3. 步骤能否稳定切分和判断？可以分类、生成解释，也可以交给形式检查器；
4. 中间状态是否值得复用？值得时使用 Beam Search、ToT 或 MCTS；
5. 多条完整解法是否更容易并行？是时再考虑 Best-of-N、PaCoRe 或生成式协调器。

这条顺序也解释了为什么 PRM 不是所有推理任务的默认答案。评价器自身会犯错，搜索会放大它的偏差，并行协调则会消耗大量 token。先建立可靠反馈，再扩大推理计算，才能让更长或更多的轨迹转化为真实能力。
