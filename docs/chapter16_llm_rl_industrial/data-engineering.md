# 18.5 大规模 RL 数据工程

[18.2](./industrial-post-training) 已经说明，工业后训练会不断把失败样本送回下一轮训练。现在顺着一条失败轨迹往回看：团队怎样找到原始任务，怎样恢复它运行时的环境，怎样判断模型完成了任务，又怎样决定这条轨迹是否值得训练。

先看一个代码任务。用户报告“点击保存后页面没有更新”。只有这句话，模型可以给出一段修改建议，却无法通过真实执行获得可靠奖励。要把它变成 RL 数据，还需要准备代码仓库、问题出现前的 commit、依赖、启动命令、测试和沙箱。模型每次读取文件、修改代码、运行测试的过程也要完整记录。测试通过以后，这条轨迹才能成为可验证的训练样本。

因此，大规模 RL 的一条数据通常包含以下部分：

```text
任务目标
  + 初始环境
  + 模型与工具的完整交互轨迹
  + 验证器给出的分项结果
  + 生成、环境和模型版本
```

这和普通 SFT 数据有明显区别。SFT 常用“问题—示范回答”；RL 数据还要能够**运行、判分、重放和追踪版本**。

## 一条 RL 数据生产线

一次工业数据生产可以拆成六步。每一步都解决一个具体问题。

```text
真实需求、公开数据或合成种子
              ↓
        1. 构造任务
              ↓
        2. 封装环境
              ↓
        3. 建立验证器
              ↓
        4. 多次采样轨迹
              ↓
        5. 过滤并标注
              ↓
        6. 进入训练或评测
              ↓
       失败分析后重新构造
```

### 1. 从真实需求构造任务

数据源决定模型最后会遇到什么问题。数学 RL 可以从竞赛题、教材和合成题开始；代码 agent 可以从 GitHub issue、PR 和 commit 开始；搜索 agent 可以从需要多网页证据的问题开始；桌面 agent 则来自真实工作流或可控模拟任务。

原始记录还不是训练任务。数据团队要把目标写清楚，去掉泄露答案的字段，并确定任务的初始状态。一个 GitHub PR 可以改写成多种任务：修复 bug、补充测试、审查补丁或优化性能。同一来源由此产生不同能力的数据，但它们必须保留共同的来源标识，防止被误当成彼此独立的样本。

### 2. 把任务封装成可恢复的环境

RL 会对同一个任务采样多次。每次采样都要从相同状态开始，否则奖励无法比较。

代码环境至少需要锁定仓库 commit、依赖版本、系统镜像、启动命令和网络权限。浏览器任务需要锁定网站快照、账号状态和可用工具。长期运行的 agent 还要保存中间文件、外部服务状态或可恢复的检查点。

环境构建失败也是一种数据结果。它说明样本尚未达到训练标准，不能简单记成模型失败。

### 3. 先验证任务，再验证模型

验证器负责把执行结果变成奖励。建立验证器时要先用已知正确方案跑一遍，确认任务确实可解；再用明显错误的方案测试，确认验证器不会轻易放过错误。

代码任务常同时使用两组测试：修复前失败、修复后通过的测试证明问题已经解决；原本就通过的测试检查修改是否破坏已有功能。应用开发任务很难预写全部测试，可以让验证 agent 启动应用、操作界面，再按可执行性、交互结果和视觉要求分别评分。

一个可靠奖励最好保留分项结果：

| 奖励项     | 它检查什么               | 失败时能定位什么问题 |
| ---------- | ------------------------ | -------------------- |
| 环境有效性 | 环境是否成功启动         | 数据或基础设施错误   |
| 任务完成度 | 核心测试或目标是否达成   | 模型没有解决主要问题 |
| 回归检查   | 原有能力是否仍然正常     | 修改带来的副作用     |
| 行为约束   | 是否越权、超时或无效循环 | 工具策略和安全问题   |
| 成本       | token、时间和工具调用量  | 完成任务是否过于低效 |

只保存一个总分，会让后续团队看不出奖励为什么变化。

### 4. 用当前模型采样完整轨迹

同一个任务要生成多条轨迹，因为模型可能尝试不同方法。轨迹应记录每一轮输入、模型动作、工具参数、环境返回、时间和终止原因。生成它的模型版本、采样参数和 agent scaffold 也必须保存。

这些版本字段直接影响训练判断。如果异步系统中的轨迹来自较早的模型，训练端需要决定是否继续使用、做重要性修正，或把它丢弃。如果同一任务只在一个 scaffold 中出现，模型还可能学会外层模板，而没有真正学会解决任务。

### 5. 过滤错误数据，保留有学习价值的失败

成功轨迹适合做 SFT 示范，也可以参加 RL。失败轨迹不能全部删除：模型在最后一步写错答案、调用了错误工具、环境中途崩溃，三种失败的训练价值完全不同。

过滤时先区分四类结果：

| 结果             | 是否进入训练 | 处理方式                           |
| ---------------- | ------------ | ---------------------------------- |
| 环境无效         | 否           | 修复环境后重新采样                 |
| 验证器不可靠     | 否           | 修改规则，并重新计算历史样本       |
| 模型失败但可学习 | 可以         | 保留轨迹、失败位置和分项奖励       |
| 模型成功         | 可以         | 检查是否利用漏洞，再进入 SFT 或 RL |

RL 还需要控制难度。模型对某道题的所有采样都成功，通常已经没有多少学习信号；所有采样都失败，可能说明任务过难或验证器有问题。DAPO 的动态采样正是优先保留组内既有成功又有失败的题目。

### 6. 分开训练集、回放集与评测集

清洗后的数据不要直接放进同一个目录。至少建立三个用途明确的数据池：

- **任务池**保存尚未采样或准备继续采样的任务和环境。
- **轨迹池**保存成功、失败和中间状态，用于 SFT、RL、蒸馏和回放。
- **评测池**只用于独立检查，不参与训练，也不能被任务合成器间接看到。

同一 GitHub 仓库、同一网页来源或同一合成模板生成的样本应按来源分组切分。逐条随机切分很容易让高度相似的任务同时进入训练集和评测集，得到虚高的结果。

## 一条轨迹至少记录什么

下面是一份适合入门的最小字段表。真实系统可以拆成多个表或对象存储，但字段之间的关系应当保留。

| 类别 | 关键字段                                                 |
| ---- | -------------------------------------------------------- |
| 任务 | `task_id`、能力域、来源、目标、难度、数据许可            |
| 环境 | 镜像或快照版本、初始状态、工具清单、网络与权限策略       |
| 生成 | 模型版本、策略版本、采样参数、scaffold、开始与结束时间   |
| 轨迹 | 每轮观察、动作、工具返回、token 数、终止原因             |
| 验证 | 验证器版本、分项奖励、总奖励、测试日志、是否需要人工复核 |
| 治理 | 去重簇、训练/评测划分、质量状态、创建时间、上游数据版本  |

其中最容易被漏掉的是**验证器版本**。规则修改后，同一条轨迹的奖励可能改变。没有版本号，团队无法解释训练曲线为什么突然变化，也无法重新计算历史数据。

## 质量检查要沿着因果链进行

数据检查不应只在导出 JSONL 时做一次。每个阶段都有自己的闸门。

1. **来源闸门**：数据是否允许使用，是否包含隐私、密钥或评测答案。
2. **任务闸门**：目标是否明确，是否能从指定初始状态完成。
3. **环境闸门**：环境能否重复启动，外部依赖是否稳定。
4. **验证闸门**：正确方案能通过，明显错误方案会失败，奖励是否容易被钻空子。
5. **轨迹闸门**：动作和工具返回是否完整，是否发生截断、超时或服务错误。
6. **训练闸门**：难度、领域、长度和成功率是否失衡，是否和评测集重合。

早期错误会传播到后面。一个依赖缺失的代码环境会让所有 rollout 失败；如果系统把它记成模型能力不足，难度调度会继续增加这类任务，训练算力便持续消耗在无效样本上。分阶段闸门的目的，就是在错误进入下游前说明它来自哪里。

## 面壁智能的 RL 与 OPD 怎样放进这条线

面壁智能与 OpenBMB 公布的 MiniCPM5-1B 采用 SFT、RL、OPD 三步后训练。RL 阶段分别训练数学、代码、闭卷问答、写作等领域教师；OPD 再把这些教师的能力合到一个发布模型。

先从直觉理解 OPD。学生模型面对一道代码题，按照自己当前的策略生成回答。教师看到学生已经生成的前缀，对下一 token 给出更合适的概率分布。学生逐步调整自己的分布。因为轨迹来自学生当前策略，教师纠正的是学生实际会遇到的状态。

这套流程复用了训练领域教师时的提示池，减少了额外题目整理。数据系统仍要补上几项记录：提示属于哪个领域、由哪个学生策略采样、使用哪个教师、蒸馏信号是否正常、训练前后长度和正确率怎样变化。教师的完整 logits 可以在线传输，不一定全部长期落盘；版本和汇总统计必须保留，才能重现实验。

OPD 解决的是“怎样把多个专家合回一个模型”。领域任务、环境和验证器仍然要先由数据工程准备好。它不能替代前面的六步生产线。

## 截至 2026 年 8 月的公开工业做法

下面只列公开材料能够确认的做法。公司没有披露的内部数据量、人工流程和混合比例，不做推断。

| 团队与公开项目   | 数据工程重点                                                        | 可以学到什么                                       |
| ---------------- | ------------------------------------------------------------------- | -------------------------------------------------- |
| 面壁 MiniCPM5    | 分领域 RL 教师、复用领域提示做 OPD、UltraData 分层管理              | 专家能力如何汇入一个小模型                         |
| Moonshot Kimi K3 | 知识图谱引导任务合成、可组合白盒环境、多阶段验证与人工复核          | 任务、工具、上下文和 scaffold 怎样一起成为训练配置 |
| MiniMax M2.1     | GitHub PR 到 Docker 环境，任务多样化，多 scaffold，验证 agent       | 真实软件事件怎样变成大规模可验证数据               |
| Qwen-AgentWorld  | 容器、MCP 与多类模拟器，下一状态预测，回合级筛选，混合奖励          | 怎样筛出轨迹中真正包含环境信息的部分               |
| 字节 Seed / DAPO | DAPO-Math-17k、动态采样、过长轨迹处理                               | 怎样把算力放在仍有学习信号的题目上                 |
| GLM-5.2 / slime  | 环境与验证器接口、持续数据缓冲、单轨迹异步 RL、策略版本管理         | 长短不一的 agent 轨迹怎样持续进入训练              |
| NVIDIA Cascade 2 | 多领域 Cascade RL、阶段性教师、On-Policy Distillation、开放 RL 数据 | 怎样用中间教师修复后续训练造成的能力回退           |

这些项目的算法各不相同，数据主线高度一致：**把任务变成可执行环境，记录当前策略的完整轨迹，用可靠验证器判分，再按难度、领域和版本选择下一批数据。**

:::: details 进阶：UltraData 分层方法怎样用于 RL 数据

面壁与清华的 UltraData 把通用数据分成 L0 到 L4：从可追溯原始数据，经过清洗去重、质量选择和深度加工，走向组织化、可验证的知识资源。论文讨论的是贯穿预训练、中期训练和对齐的数据管理，并没有把 RL 轨迹直接定义成另一套 L0 到 L4。

在 RL 工程里可以借用它的“分层而不覆盖上游”思想：

| 借用后的层级 | RL 数据示例                                          |
| ------------ | ---------------------------------------------------- |
| 原始层       | issue、PR、网页、用户任务或公开题目                  |
| 清洗层       | 去重、脱敏、许可检查、来源可追踪的任务候选           |
| 可执行层     | 已锁定环境、工具和验证器，能够重复运行的任务         |
| 轨迹层       | 带模型版本、环境返回和分项奖励的成功与失败轨迹       |
| 训练层       | 已按难度、领域和用途分桶，可用于 SFT、RL、OPD 或评测 |

这张表是对 UltraData 思想的工程化迁移，并非论文给出的 RL 官方分级。关键原则是保留上游：如果只保存最终训练 JSONL，验证规则出错时就无法回到原始任务重建数据。

:::: details 进阶：OPD 的训练信号

设学生在前缀 $x_{<t}$ 下给出的分布为 $p_\theta(\cdot\mid x_{<t})$，教师分布为 $q(\cdot\mid x_{<t})$。MiniCPM5 公布的实现使用反向 KL：

$$
D_{\mathrm{KL}}\!\left(p_\theta\|q\right)
=
\sum_a p_\theta(a\mid x_{<t})
\log\frac{p_\theta(a\mid x_{<t})}{q(a\mid x_{<t})}.
$$

学生先按 $p_\theta$ 采样轨迹，再在每个位置比较学生与教师分布。为了减少计算与通信，MiniCPM5 取学生和教师各自的 top-k token，并在二者并集上近似计算。这个信号比只在回答结束时给一个 0/1 奖励更密集。

数据侧要特别检查三件事：学生轨迹和教师评分使用同一 tokenizer；教师与学生的 chat template、工具协议一致；每条轨迹能追踪到明确的教师和学生版本。任一项发生漂移，逐 token 信号都会失去可比性。

::::

:::: details 进阶：数据监控与故障定位

训练看板除总奖励外，至少保留下列指标：

- **环境成功率**：环境启动、依赖安装和服务调用是否正常。
- **有效轨迹率**：排除服务错误、截断和格式损坏后，还剩多少轨迹。
- **任务成功率分布**：按领域、难度、来源和环境版本观察，避免平均数掩盖局部失败。
- **组内奖励方差**：判断一批任务是否还有可学习信号。
- **验证器分歧率**：规则、模型裁判和人工复核之间是否开始产生系统性分歧。
- **轨迹长度与成本**：成功率提高时，token、时间和工具调用是否失控。
- **策略陈旧度**：轨迹生成版本落后当前训练版本多少步。
- **重复与评测污染**：新数据是否和已有任务、评测题或同源变体重合。

出现奖励突升时，先检查环境成功率和验证器版本，再检查模型能力。验证器变宽、测试服务超时后默认通过、网页快照改变，都可能制造虚假的奖励提升。

::::

## 本节小结

- 大规模 RL 数据的基本单位是任务、环境、轨迹、验证结果和版本信息的组合。
- 数据生产依次经过任务构造、环境封装、验证器建立、轨迹采样、过滤标注和训练划分。
- 任务池、轨迹池和评测池用途不同；同源样本应分组切分，防止评测泄漏。
- OPD 可以合并多个领域教师的能力，前提仍是先准备可靠的领域任务、环境和提示池。
- 数据工程的目标是让每次奖励都能解释、每条轨迹都能重放、每轮失败都能进入下一轮改进。
