# 16.4 Hybrid Thinking 与预算控制

16.3 节说明同一个模型可以用更多候选、修订或搜索换取更高成功率。现在把两条请求放进同一个服务队列：第一条是“把 hello 翻译成中文”，第二条是“证明某个数列收敛”。若都进入长思考模式，翻译请求白白增加延迟；若都直接回答，证明题又容易在中间步骤出错。

**Hybrid Thinking** 让同一模型支持直接回答和深度思考两种行为。问题也随之分成三层：训练时怎样让两种模式共存，推理时怎样选择把预算用于一条长链还是多个短答案，模型已经会长思考以后怎样把冗余步骤压缩。最后，部署系统还要保证模式切换、答案一致性和预算耗尽时的收尾都可控。

## 1. 同一模型如何支持两种模式

最容易想到的方案是维护两个模型：一个负责快速回答，一个负责复杂推理。这样会带来两套权重、两套部署和能力不同步的问题。Hybrid Thinking 改为共享同一组参数，再用训练样本或控制标记指定当前模式。

### 1.1 DeepSeek V3.1 怎样提供两种模式

[DeepSeek V3.1](https://api-docs.deepseek.com/news/news250821)（2025.08）公开展示了这种接口：同一个模型支持 Think 与 Non-Think 两种模式，API 分别通过 `deepseek-reasoner` 和 `deepseek-chat` 暴露。公开说明能够确认的是单模型双模式、思考效率与工具能力改进，没有披露每一种训练数据和损失细节。

- **同一个模型**：不维护两个独立的"思考模型"和"非思考模型"
- **模式切换**：请求路由到思考或非思考接口；
- **共享能力**：两个模式来自同一模型版本，知识和工具能力可以同步更新。

要训练这样的模型，数据至少要同时覆盖长推理回答和直接回答，否则一个模式会挤压另一个模式。模式由用户、模板还是模型自动选择，则取决于产品接口，不能只由“双模式”这一结果反推出具体训练流程。

### 1.2 Qwen3 怎样训练两种输出

[Qwen3 技术报告](https://arxiv.org/abs/2505.09388)（2025.05）提出了更系统的 Hybrid Thinking 方案。Qwen3 全系模型（从 0.6B 到 235B）都支持两种模式：

Qwen3 用同一组模型参数学习两类输出。聊天模板或用户设置告诉模型当前应生成长推理还是直接回答：

- 训练数据中混合了 thinking 和 non-thinking 两种样本
- thinking 样本：完整的长 CoT + 答案
- non-thinking 样本：直接的短答案
- 通过模板控制是否启用 thinking

共享参数避免维护两套完全独立的模型，但选择模式仍然需要请求设置或上层路由。模型不能只根据“看起来像数学题”就保证做出最省成本的决定，16.5 节会继续处理这个问题。

### 1.3 Thinking Budget 怎样限制思考长度

Qwen3 技术报告进一步讨论 **thinking budget**：部署端给推理过程分配 token 预算，用同一模型形成不同的质量—延迟工作点。不同推理服务的参数名和实现可能不同，下面用伪代码表示接口含义：

```python
# Qwen3 thinking budget 示例
response = client.chat.completions.create(
    model="qwen3-235b-a22b",
    messages=[{"role": "user", "content": "证明根号2是无理数"}],
    extra_body={"thinking_budget": 2000}  # 服务端示意参数
)
```

这个上限直接影响三项部署指标：

- 小预算缩短高频请求的等待时间；
- token 上限限制一次调用的最坏成本；
- 大预算给难题留下更多检查和修订空间。

预算控制还会带来截断问题：若系统直接在证明中间停止生成，剩余 token 不足以写出最终答案。训练和部署因此要分别处理长度效率、停止条件与答案保留；不能把一个 API 上限等同于模型已经学会在任何截断点正确收尾。

## 2. 长思考和并行短回答如何选择

进入“需要更多计算”的任务以后，仍然要决定计算怎样花。对知识问答，多次短回答投票可能已经足够；对需要连续证明的题目，一条能够保留中间状态的长链更有价值。NoThinking 实验正是在相同预算下比较这两种分配。

2025 年 4 月，Ma et al. 在 [Reasoning Models Can Be Effective Without Thinking](https://arxiv.org/abs/2504.09858) 中比较了长思考与 NoThinking。论文使用 DeepSeek-R1-Distill-Qwen 系列模型，发现在低 token 预算或低延迟条件下，多次较短回答可以成为有竞争力的方案。

### 2.1 怎样在相同预算下比较两种方法

实验控制总 token 或墙钟延迟，对比两种方式：Thinking 用较长轨迹完成一次或少量尝试；NoThinking 跳过显式长推理，独立生成更多完整答案，再用任务验证器或置信度选择。论文覆盖数学、形式证明和代码等七类任务，结论集中在低预算区间，不能改写成“NoThinking 在所有任务上更好”。

### 2.2 NoThinking 为什么在部分任务上有效

一条长链把预算集中在同一个解法上，早期选错方向时，后面的计算会继续依赖错误前缀。多个短回答把预算分散到不同起点，覆盖的方法更丰富。它也依赖两个条件：短回答本身要有一定成功率，系统还要能够判断哪个答案更好。单次成功率太低或任务缺少 verifier 时，增加短答案数量未必有用。

这组实验比较的是两种计算分配：把预算用于延长一条推理链，或用于增加独立候选。题目容易、单次正确率已经不低时，多采样更容易覆盖正确答案；题目需要连续推导时，长推理更有价值。选择方式要同时看任务难度和 verifier 是否可靠。

## 3. Long2Short 如何压缩推理链

长思考训练首先追求成功率，模型因而可能学会反复检查和重复表述。部署时不能只用硬截断解决：截断点若落在结论以前，模型甚至来不及输出答案。Long2Short 的目标是让模型在训练阶段学会保留必要步骤、删除冗余步骤。

推理 RL 可能让回答逐渐变长，因为更长轨迹提供了更多尝试、检查和恢复机会。这有三个直接原因：

- **奖励信号鼓励"答对"**，更长 CoT 意味着更多检查机会，答对概率更高
- **反思和验证行为被强化**，模型学会"再检查一遍"
- **没有显式的长度约束**，模型没有动机压缩 CoT

长度增加只有在提高正确率时才有价值；重复表述和无效检查会直接增加部署成本。这就产生了 long2short 问题：怎样把长推理中已经学到的规划和修正能力转移到较短回答中，同时保留任务成功率？

[Kimi k1.5](https://arxiv.org/abs/2501.12599) 比较了四种具体方法：模型权重合并、Shortest Rejection Sampling、DPO 和 long2short RL。它们分别从模型参数、监督样本、偏好数据和 RL 奖励入手。

### 3.1 从长模型得到短回答监督

同一道题多次采样时，正确回答的长度往往不同。Shortest Rejection Sampling 从多条正确回答中选择最短的一条做 SFT；DPO 则把较短正确回答作为偏好样本，把更长或错误回答作为被拒样本。这两种方法都先保证答案正确，再学习长度差异，避免模型只靠省略步骤获得短奖励。

模型权重合并走的是另一条路：直接平均长、短 CoT 模型的权重，观察长推理能力能否部分迁移到短模型。它不生成新的压缩文本，也不保证合并后的每项能力都处在两者之间，因此仍需完整评测。

### 3.2 在 RL 中比较同组回答长度

long2short RL 从已经取得较好正确率与长度平衡的模型继续训练，并缩短允许的 rollout 长度。Kimi k1.5 的长度奖励在同一道题的一组回答中做相对比较：正确回答越短，长度奖励越高；错误回答不能仅凭更短得到正奖励。

设第 $i$ 条回答长度为 $\operatorname{len}(i)$，组内最短和最长长度分别为 $l_{\min}$、$l_{\max}$，先计算

$$
\lambda_i=0.5-\frac{\operatorname{len}(i)-l_{\min}}{l_{\max}-l_{\min}}.
$$

$\lambda_i$ 随回答变长而下降，再结合答案是否正确决定最终长度奖励。若组内长度完全相同，就把长度项设为 0。这个设计学习的是“在同样能解题的回答中偏好更短者”，不需要先规定所有题共享一个固定目标长度。

### 3.3 比较压缩前后的效果

论文报告 long2short RL 模型在 AIME 2024 上得到 60.8 的 Pass@1，平均使用 3,272 token。这个数字只说明给定实验中的质量—长度工作点；选择部署模型时仍要绘制完整曲线，而不能只比较一个分数。

### 3.4 训练压缩与推理预算怎样配合

long2short 和 thinking budget 是互补的：

- **long2short** 是**训练阶段**的压缩——改变模型本身，让它倾向于生成短 CoT
- **thinking budget** 是**推理阶段**的控制——不改变模型，用服务上限限制单次计算

部署时可以组合两种控制：

```text
训练阶段：long2short RL 让模型学会短 CoT
推理阶段：thinking budget 设一个安全上限
```

## 4. 部署时如何控制模式与预算

训练得到两种模式和较短推理链以后，最后才轮到服务接口。一次请求需要依次完成三项决定：是否进入思考模式，最多允许多少计算，预算结束时怎样产出完整答案。

模式开关确定以后，训练和部署还要解决三个问题：怎样选择模式、怎样检查两种模式的能力差异，以及预算结束时怎样收尾。

### 4.1 判断是否需要思考

用户可以显式选择模式，也可以由路由器根据任务、历史成功率和延迟目标选择。若让模型参与判断，仍应把决定记录下来，并分别评测误开长思考和误关思考的代价。

### 4.2 保持两种模式的答案一致

同一道确定性问题在两个模式下出现冲突，说明至少有一条路径不可靠。训练时可以加入共享数据或一致性目标，部署时则应分别评测两种模式，不能假设共享参数自然保证答案相同。开放问题允许表达不同，评价重点应放在事实和任务结果，而非逐字一致。

### 4.3 在预算用完时结束推理

硬截断会让回答停在中间步骤。更稳妥的接口会为最终答案预留 token，并在接近预算时触发收束；训练数据也可以覆盖不同预算条件。若预算耗尽仍没有可靠结论，系统应返回未完成状态或降级方案，不能把任意中间结论包装成确定答案。

## 小结

Hybrid Thinking 用模式切换避免简单任务产生不必要的长推理，思考预算则为复杂任务设置计算上限。long2short 从训练阶段缩短推理链，二者可以配合使用。

四个案例分别解决不同层的问题：

- **V3.1**：同一模型提供 Think 与 Non-Think 接口
- **Qwen3**：Thinking Mode Fusion + thinking_budget 参数
- **Kimi k1.5**：long2short RL 主动压缩 CoT
- **NoThinking 研究**：比较把相同预算用于一条长链或多条短回答

固定的模式开关仍然需要用户或路由器预先判断任务难度。[16.5 自适应思考](./adaptive-thinking) 进一步让模型根据输入动态决定推理深度。
